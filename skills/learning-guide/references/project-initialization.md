## 完成定义

学习项目准备完成必须同时满足：

1. 学习目标描述为可执行能力，而非“了解某主题”。
2. 已识别前置知识、范围边界和时间约束。
3. 学习内容按依赖关系分阶段，不只是罗列目录。
4. 每阶段都有学习材料、主动练习、可观察产出和验收标准。
5. 第一个学习单元足够具体，可以立即开始。
6. 项目已由 CLI 注册，核心文件不存在占位符。
7. 至少一个高价值内容已进入复习体系，或明确说明为何暂不创建。

只有目录创建成功不能称为初始化完成。

## 输入诊断

优先从用户请求和现有材料推断；只有答案会实质改变路线时才提问。最多集中确认以下信息：

| 维度 | 必须得到的答案 | 影响 |
|---|---|---|
| 目标能力 | 最终要能完成什么真实任务 | 决定终点和项目 |
| 当前基础 | 已经能解释或完成什么 | 决定起点和是否补先修 |
| 使用场景 | 工作、考试、兴趣、项目或研究 | 决定深度与题型 |
| 时间预算 | 每周时长、期限、单次时长 | 决定阶段数量和颗粒度 |
| 学习偏好 | 文档、书籍、视频、代码或实验 | 决定资源组合，不替代主动练习 |
| 环境限制 | 操作系统、硬件、软件、权限和成本 | 决定实验能否执行 |

信息不完整但风险较低时，写明假设并继续。不要为收集偏好阻塞一个可以安全开始的项目。

## 项目设计

### 1. 定义目标和边界

使用以下格式：

```text
目标能力：能够在什么条件下，完成什么任务，达到什么质量。
适用场景：为什么学习、在哪里使用。
不包含：本阶段明确不学什么。
完成证据：作品、运行结果、解释、测验或真实任务。
```

### 2. 建立知识依赖图

先列能力，再倒推知识：

```text
最终任务
├─ 必需概念
├─ 必需操作
├─ 必需诊断能力
└─ 必需权衡能力
```

对每个单元标记：先修、输入材料、练习、产出和常见失败。按依赖排序，不能只照书籍目录复制。

### 3. 划分里程碑

每个阶段控制在一个可验收能力跃迁：

| 字段 | 要求 |
|---|---|
| 阶段目标 | 动词开头，可观察 |
| 核心问题 | 2–5 个必须回答的问题 |
| 学习内容 | 只列支撑问题所需内容 |
| 主动练习 | 回忆、解释、操作、分析或设计 |
| 阶段产出 | 笔记、代码、实验报告、图或讲解 |
| 验收标准 | 正确性、独立性、边界和质量门槛 |
| 预计投入 | 阅读、实践和复习分别估算 |

### 4. 设计首个学习单元

首个单元应在一次会话内完成，包含：

- 一个明确问题；
- 必需的最少材料；
- 一个探测题；
- 一个应用任务；
- 一个完成标准；
- 下一次复习入口。

## 创建与注册

### 新项目

1. 用 `learn new <topic> [--path <path>] --json` 创建受管项目。
2. 读取返回的项目路径和名称，不猜测。
3. 检查生成的目录和 CLI 状态：`learn status <project> --json`。

### 已有目录

1. 先确认目录确实是用户指定的学习项目。
2. 检查已有 README/MOC、进度、笔记、资源和项目内容。
3. 用 `learn project import --path <dir> [--name <name>] [--topic <topic>] --json` 注册。
4. 导入不得覆盖现有知识文件；出现冲突时先报告。

## 内容落地

CLI 模板生成后，必须进行主题化改写。以下顶层结构是与 CLI 的数据契约，不得另造同义的平行目录或文件：

```text
README.md 或项目入口
progress.md
notes/
knowledge/
flashcards/deck.json
projects/
resources/
reviews/review-index.json
reviews/review-history.json
reviews/session-history.json
```

内容映射固定如下：

| 内容 | 固定位置 | 不要另建 |
|---|---|---|
| 总目标、路线、阶段和验收 | `README.md`；知识库要求 MOC 时可用 MOC 作为内容入口，但保留 CLI 所需 README | `learning-plan.md`、`roadmap.md` |
| 状态、实际时长、阻塞和下一步 | `progress.md` | `status.md`、`study-log.md` |
| 单次学习笔记 | `notes/` | `lessons/` |
| 可复用概念与机制 | `knowledge/` | `concepts/`，除非宿主知识库强制规定 |
| 实验、代码、报告与能力证据 | `projects/` | `labs/`、`evidence/` |
| 书籍、文档、课程与来源说明 | `resources/` | 根目录 `references.md` |
| 内联闪卡 | 通过 CLI 写入 `flashcards/deck.json` | 手工维护 `flashcards.md` |
| 调度、复习与会话历史 | 通过 CLI 写入 `reviews/*.json` | `review-log.md` |

只有宿主仓库存在明确规则时才调整内容文件的位置；即便调整，也必须保持 CLI 能注册和解析的数据文件，并在项目入口说明映射。不要因为个人偏好发明第二套状态或复习体系。

至少完成：

- 入口文件：目标、假设、边界、路线、阶段验收、首个动作。
- 进度文件：当前状态、下一步、阻塞、里程碑表；不伪造学习时长。
- 资源文件：资源用途、版本、适用阶段和选择理由。
- 实践入口：至少一个与最终能力一致的任务及验收标准。
- 笔记目录：建立首个主题入口；不要预生成大量空笔记。
- 项目目录：将实验、代码和验收证据放在同一个任务目录中，例如 `projects/java-connect/`，不要拆成平行的 `labs/` 与 `evidence/`。

如果项目位于已有知识库，先读取该知识库的贡献和链接规则，再选择 README、MOC 或其他入口格式。CLI 状态文件与知识库内容文件的职责必须明确。

## 初始化复习系统

项目创建时不要批量生成未经学习的闪卡。只允许：

- 为已确认的前置知识创建诊断性复习项；
- 将高质量路线或首个项目作为引用式复习入口；
- 在实际学习后创建基于用户错误和关键边界的闪卡。

通过 `learn flashcard add-note/add-knowledge/add-project` 注册引用内容。CLI 成功返回前，不声称已排期。

## 验收清单

完成前逐项检查：

- [ ] 项目名、路径、主题和 CLI 索引一致。
- [ ] 顶层结构遵循 CLI 契约，没有同义的平行计划、实验、证据或复习目录。
- [ ] 目标是可观察能力，完成证据明确。
- [ ] 前置知识和不学范围明确。
- [ ] 路线按依赖排序，每阶段有产出与验收。
- [ ] 时间预算现实，阅读、实践、复习都有占比。
- [ ] 资源包含版本与用途，没有无筛选链接堆积。
- [ ] 第一个学习单元可立即执行。
- [ ] 至少一个实践项目与最终目标一致。
- [ ] 所有模板占位符已删除。
- [ ] CLI `status` 能读取项目；写入结果均已核对。
- [ ] 新增文件通过仓库自身检查。

任一关键项不满足时，说明项目处于“草稿”或“待准备”，不要宣称完整。
